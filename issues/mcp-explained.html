Deep Dive Nº 05 · The Plumbing

MCP: the USB-C port for AI

Chatbots got clever a while ago. What changed recently is that they can now reach your files, your calendar and your code. One quiet open standard is the reason why, and it spread across the whole industry in barely a year.

The Student AI Brief 6 min read 19 July 2026 The Plumbing series

An AI assistant that can only talk is a party trick. It writes a decent essay, drafts a plausible email, and then stops at the edge of the chat box, unable to touch anything real. The leap from a clever talker to something genuinely useful comes down to a boring-sounding word: integration. The assistant has to reach your actual notes, your actual calendar, your actual repository. And for most of AI's short history, wiring up each of those connections was a bespoke, brittle nightmare. The Model Context Protocol, or MCP, is the standard that made the wiring disappear.

If you have heard the phrase "USB-C port for AI," that is MCP, and the analogy is worth taking literally. Before USB-C you had a drawer of incompatible cables: one for the printer, another for the camera, a third for the phone. USB-C replaced them with a single shape that any device could speak. MCP does the same thing for AI assistants and the tools they want to plug into.

The one-line version

MCP is an open standard that gives an AI assistant a single, common way to plug into external tools, apps and data sources. Build one MCP connector for your app, and every MCP-speaking assistant can use it. No more one custom integration per assistant per tool.

The problem it solvesWhy every connection used to be bespoke

Picture the mess without a standard. You have a handful of AI assistants and a pile of tools you want them to reach: Google Drive, GitHub, your notes app, a database. Connecting them by hand means building a separate custom bridge for every pairing. Ten tools and five assistants is fifty integrations, each maintained forever. This is the "M times N" problem, and it was quietly killing agent projects before they shipped.

MCP turns that multiplication into an addition. Each tool exposes itself once, through an MCP server. Each assistant learns to speak MCP once, as an MCP client. After that, any client can talk to any server without knowing anything special about it, the same way any USB-C laptop charges from any USB-C charger.

Why it matters nowAgents are only useful if they can DO things

The whole industry spent 2025 and 2026 talking about agents: AI that does not just answer but acts on your behalf. Books a slot, opens a pull request, reconciles a spreadsheet. An agent that cannot reach your stuff is a daydream. MCP is the layer that lets it reach, in a controlled and inspectable way, which is why the excitement around agents and the adoption of MCP arrived hand in hand.

Concretely, an MCP server can expose three kinds of thing to an assistant: tools it can call (send an email, run a query), resources it can read (a file, a calendar), and prompts it can reuse. The assistant sees a tidy menu and picks from it. That is the entire trick, and its plainness is the point.

A model that can only produce words is an oracle. A model that can safely reach your tools is an assistant. MCP is the difference between the two.

Where it came fromAn Anthropic idea the rivals adopted

MCP was introduced by Anthropic, the company behind Claude, in November 2024, and released as an open standard rather than a proprietary hook. That decision mattered. Because anyone could implement it, the competition did. OpenAI adopted MCP in March 2025, wiring it across ChatGPT and its developer platform. Google confirmed support across Gemini soon after, and Microsoft built it into Windows and its developer tooling at Build 2025.

Rivals converging on a competitor's format is rare, and it is the strongest signal that a standard has genuinely won. In December 2025 Anthropic handed governance of MCP to the Agentic AI Foundation, a fund under the Linux Foundation co-founded with OpenAI and Block, so no single company owns the port everyone now depends on.

Treat the 97 million figure as a direction, not gospel: it comes from ecosystem reporting rather than an audited count, and downloads are not the same as active users. But the shape of the curve is not in doubt. Reporting put MCP at that level roughly sixteen months after launch, a faster ramp than most infrastructure standards ever manage.

The catchA universal port cuts both ways

Here is the part the hype tends to skip. A standard that lets an assistant plug into anything also lets it plug into something malicious. MCP moved fast, and its security story is still catching up. Two problems deserve your attention before you install a random server you found on the internet.

  • Tool poisoning. An assistant decides which tool to call partly by reading the tool's description. A hostile MCP server can hide instructions inside that description, text you never see, telling the model to quietly copy your files or leak a secret. The tool looks normal in the menu and misbehaves once selected.
  • Over-permissioning. A server you grant broad access can do broad damage, whether through malice or a bug. Give a connector your whole inbox and file store, and a single successful prompt injection has a large blast radius.

These are not theoretical. In April 2026 researchers at Johns Hopkins hijacked Claude Code, Gemini CLI and GitHub Copilot by planting malicious instructions inside GitHub pull-request titles; the agents read the poisoned text as part of their task and exfiltrated repository secrets. The lesson is not "avoid MCP." It is "treat an MCP server like software you are about to run with your permissions," because that is exactly what it is.

Before you plug anything in

Install servers from sources you trust, the same way you would a browser extension. Grant the narrowest access that does the job, not blanket permissions. And prefer clients that show you each action before it runs, so a poisoned tool has to get past you, not just past the model.

For the student builderWhat to actually do with this

The reason to care as a student is that MCP is the cheapest on-ramp to building something that feels like magic. You do not need to train a model or host anything heavy. You point an assistant at a few servers and it can suddenly reason over your real material:

  • Your notes. Connect a filesystem or notes server and ask your assistant to pull threads across a term of lecture notes, not just the one file in front of you.
  • Your calendar and email. Let it draft replies and find a free slot, with you approving each send.
  • Your code. A GitHub or filesystem server turns a coding assistant into one that reads your actual repository, opens issues and proposes changes you review.

Start read-only. Wire up one server, keep it to things the assistant can look at but not change, and watch what it does. Add write access only once you trust both the server and the client's guard-rails. That single habit, read before write, narrow before broad, is most of MCP security in practice.

The takeawayThe mental model to keep

MCP is the port, not the intelligence. The model still does the thinking; MCP is the agreed shape that lets that thinking reach the world without a tangle of custom cables behind it. Boring, universal plumbing is exactly what a chaotic new field was missing, which is why it spread so fast.

So when you next hear that some assistant "supports MCP," read it the way you read "USB-C" on a gadget box. It means this thing plugs into the same ecosystem as everything else, no special cable required. Just remember that a universal port carries whatever you connect to it, so choose what you plug in with care.
